# E Top — social marketplace

E Top keeps the social feed, short videos, profiles, follows, chat, and calls separate from the Shop. Product browsing, seller tools, cart, wishlist, orders, checkout, and payment return pages are all contained under `/shop`.

## Run locally

Requirements: Node.js, npm, and a MongoDB database.

1. Copy the root `.env.example` to `.env`, then set `MONGO_URI` and a strong, private `JWT_SECRET`.
2. Copy `frontend/.env.example` to `frontend/.env`. Keep the local API and Socket.IO URLs for local development.
3. Install and start the backend from the repository root:

   ```sh
   npm install
   npm run dev
   ```

4. In a second terminal, install and start the frontend:

   ```sh
   cd frontend
   npm install
   npm start
   ```

The frontend is served at `http://localhost:3000`; the API health endpoint is `http://localhost:5000/api/health`.

## Production services

- Set `CLIENT_URL` to the deployed frontend origin. Add any other exact frontend origins to `CORS_ORIGINS`, separated by commas.
- To enable Google registration and sign-in, create a Google OAuth 2.0 Web client and set its client ID as `GOOGLE_CLIENT_ID` on the backend and `REACT_APP_GOOGLE_CLIENT_ID` on the frontend. Add each deployed frontend origin to the OAuth client's authorized JavaScript origins, then rebuild and redeploy the frontend after setting its variable. The backend verifies every Google ID token and its verified email before creating or connecting a customer account; never put a Google client secret in frontend configuration.
- Configure Cloudinary (`CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET`) in the backend host's environment before deploying if users need persistent profile photos, posts, reels, or message attachments including voice notes. Without it, media uses local disk and may be lost when the host restarts or redeploys. When Cloudinary is configured, retrying an older local voice note migrates it to persistent storage if its original upload still exists; files already removed from ephemeral storage cannot be restored. Profile/post photos are limited to 10MB; reels are limited to 80MB and 5 minutes.
- Configure SMTP (`EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_SECURE`, `EMAIL_USER`, and `EMAIL_PASS`) in the backend host to deliver password-reset codes; use an email-provider app password where required. Optionally set `EMAIL_FROM` and `EMAIL_LOGO_URL` (otherwise the email logo uses `CLIENT_URL/brand/etop-loading-logo.png`, which must be publicly reachable). Password-reset codes expire in 10 minutes, are limited to five attempts, and new codes are throttled for 60 seconds. Password reset issues a one-time token and revokes linked device sessions. Registration does not require email verification and creates a social account with the default customer role; seller access is a separate Shop workflow, not a signup choice.
- SSLCommerz checkout is sandbox-only. In Render's backend environment set `SSLCOMMERZ_MODE=sandbox`, `SSLCOMMERZ_SANDBOX_STORE_ID`, `SSLCOMMERZ_SANDBOX_STORE_PASSWORD`, `SERVER_URL` (the public HTTPS backend origin), and `CLIENT_URL` (the frontend origin). Store credentials only in backend environment variables; never add them to frontend variables or source control. The backend sends success, failure, cancellation, and IPN callbacks to its own routes; for successful IPNs it calls the official Order Validation API using the configured sandbox Store ID/password and compares the transaction ID, validation ID, amount, currency, and associated pending order before marking payment as paid. The customer success redirect alone never marks an order paid. `SSLCOMMERZ_LIVE_STORE_ID` and `SSLCOMMERZ_LIVE_STORE_PASSWORD` are reserved and unused; live mode is explicitly rejected in code. Do not set production credentials or enable live mode without separate approval.

  To test, obtain sandbox credentials at [SSLCOMMERZ Sandbox Registration](https://developer.sslcommerz.com/registration/), add the environment variables above to the backend service in Render, and redeploy the sandbox-capable backend. Use a publicly reachable HTTPS `SERVER_URL` so SSLCOMMERZ can call `/api/payment/ipn`, then place a Shop order and complete a sandbox payment. The official sandbox card examples are VISA `4111111111111111`, Mastercard `5111111111111111`, or American Express `371111111111111`, with expiry `12/26`, CVV `111`, and mobile OTP `111111` or `123456` where prompted; use only the current test values published in the [official SSLCOMMERZ documentation](https://developer.sslcommerz.com/doc/v4/#order-validation-api). Verify the frontend only shows a successful payment after `/api/payment/status/:transactionId` reports `paid`, and confirm the order history and Shop notifications update. Also exercise a failed/cancelled sandbox attempt and confirm it is not marked paid. Sandbox orders are tagged in the database and excluded from the admin payout queue; the backend rejects payout approval and manual transfer records for them. Run the backend's TLS check from its host with `curl https://sandbox.sslcommerz.com/public/tls/`; SSLCOMMERZ requires TLS 1.2 or later. This integration has not yet been tested against the merchant's sandbox account; live transactions, automated refunds, seller payouts, and escrow are not enabled.
- Set frontend `REACT_APP_API_URL` to the backend URL (with or without `/api`). If Socket.IO runs on a different host, set `REACT_APP_SOCKET_URL` too. Rebuild the frontend after changing `REACT_APP_*` values.
- For a Render Static Site, use `frontend` as the root directory, `npm ci && npm run build` as the build command, and `build` as the publish directory. In the Render Dashboard, add a rewrite rule with source `/*` and destination `/index.html` so React Router routes such as `/shop` load on direct visits and refresh. The included `frontend/public/_redirects` file is for hosts that support that file; Render's route rule must be configured in the Dashboard.
- Video and voice calls require HTTPS. The built-in public TURN fallback is best-effort; configure a dedicated TURN service with the frontend build-time `REACT_APP_TURN_URL`, `REACT_APP_TURN_USERNAME`, and `REACT_APP_TURN_CREDENTIAL` settings for reliable calls across mobile-carrier and restrictive NAT networks.
- Messenger group chats use the authenticated `/api/groups` endpoints and JWT-authenticated Socket.IO connections. Deploy the frontend and backend together so group membership notifications and realtime chat use the same release.
- Group admins can optionally enable end-to-end encryption for group text, media, and calls after every current member has registered an encryption key. Each group message uses a fresh content key wrapped individually for current members; each attachment is independently encrypted in the browser, and its filename, MIME type, caption, and decryption key are included only in the encrypted message. Encrypted-group calls use LiveKit's E2EE media/data-channel transforms and a random call key wrapped separately for every current member; only those encrypted envelopes are stored server-side, and keys expire after 12 hours of call inactivity (an active room extends the key). Membership or encryption-setting changes invalidate the key and end the active room. Encrypted-group calls fail closed on browsers that do not support LiveKit E2EE—there is no unencrypted fallback. Members added later cannot decrypt earlier messages, media, or calls. Group details show a verification code derived from all member public keys; compare the full code with every member through a trusted channel before treating their identities as independently verified.
- Direct and group Messenger history loads the newest 50 messages first; the “Load older messages” control fetches additional pages. The API accepts `page` and `limit` query parameters and caps each page at 100 messages.
- Direct-call signaling is bound to the authenticated socket user and the exact two-person conversation; calls are rejected if either person has blocked the other.
- Messenger messages can be deleted only for the current user or for everyone. Delete-for-everyone is sender-only and available for 15 minutes; delete-for-me hides the message from that user's history without removing it for other participants. Direct voice/video call events and completed group calls are stored as typed chat history entries so they remain after refresh; group call entries show the initiator's elapsed time and participant count. Group call logs store this metadata as group-chat history; call media remains end-to-end encrypted when enabled.
- Messenger status updates support text, photos, and videos, expire after 24 hours, and default to followers-only visibility; users can opt into public visibility. Status views are recorded once per viewer. Configure persistent media storage for status photos/videos to survive backend redeploys.
- Messenger device sessions are tied to the same E Top account. Users can log out another registered browser/device; older sessions must sign in again after this update before they appear in linked-device management. Encrypted chat history on a new device requires restoring the existing passphrase-encrypted key backup. Revoking a device blocks its registered API/socket session but cannot erase files or keys already copied to that device.
- Messenger text messages that cannot reach the API are saved in a per-account browser outbox (up to 100) and retried when connectivity returns; queued encrypted messages are stored as ciphertext. Attachments and voice notes still require an active connection.
- Background Web Push needs VAPID keys on the backend (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`) and the matching public key at frontend build time (`REACT_APP_VAPID_PUBLIC_KEY`). Generate a pair with `npx web-push generate-vapid-keys`, keep the private key only in backend secrets, and rebuild the frontend after setting its public key. Browser permission is opt-in per device. iPhone/iPad web push requires an installed Home Screen web app and a supported iOS version; when push is not configured, the API reports that explicitly. Message push previews are generic and do not include message content.
- Communities support public membership and private admin-approved requests. Community posts are kept out of the global/profile feed, and private community posts are available only to members.
- Admin Control's Shop tab can pause product browsing and checkout and require approval for new or seller-edited products. Approval settings are stored in MongoDB; pending products remain hidden until an admin approves them.
- Customers can apply for seller access with basic store/contact details; an administrator must approve the application before seller routes become available. Pending products can be rejected with a seller-facing note. Seller-managed shipment statuses, tracking details, and delivery notes are stored per seller shipment; these are manually entered and are not courier-verified events. Seller shipment changes follow validated forward-only transitions after payment verification, and the order records an actor-attributed status history. Checkout requires an idempotency key, and the backend rejects key reuse with a different cart/address and prevents concurrent duplicate orders. MongoDB creates the supporting uniqueness indexes on backend startup.
- Shop hides seller profiles from public product and buyer order responses and does not expose buyer account profiles to sellers. Sellers only receive the name and delivery address needed for fulfillment. Public product browsing supports bounded server-side search, category filtering, sorting, and pagination; buyer and seller order history is paginated too. Sellers can define up to 100 product variants with a unique per-seller SKU, name, price, and stock; variant selection and price/stock are validated again at checkout, and reservation release restores both variant and aggregate stock. Admins can inspect variant-stock inconsistencies through `GET /api/products/admin/inventory/reconciliation` (read-only; it reports mismatches and does not alter stock). Verified product reviews are limited to buyers with a paid order and confirmed delivery, and one review per product/order/buyer is enforced by a unique database index. Checkout reserves current inventory and verifies prices and whole-number quantities on the server; unpaid reservations expire after 30 minutes and a backend cleanup job cancels the order and releases its stock. Expiry and buyer cancellation update the order and stock in one MongoDB transaction, so the database must support transactions (MongoDB Atlas or another replica set). Legacy unpaid orders without an expiry timestamp use their creation time for the 30-minute cutoff. Customers can submit a full-order refund request for a paid order before any seller payout has been sent. An administrator reviews it, rejects it with a note, or records a completed manual refund after processing it outside the Shop; this is not an automatic SSLCommerz refund or a return-shipping workflow. Buyers may report a delivery issue within 14 days of delivery while the related seller payout remains held or ready. Open disputes block shipment changes, buyer/seller confirmations, payout approval, and manual transfer recording. The seller can submit one response; an administrator may close the issue or refer the full order to the existing refund review. Referral does not issue a refund. Pending refund requests pause seller payout processing, and completed refunds cancel unpaid seller payouts and change the order's payment status to refunded so it is excluded from paid-revenue analytics. Payout eligibility is bookkeeping only: it does not mean the Marketplace or payment provider holds funds. Both buyer and seller must confirm delivery/payout details before an administrator can approve a payout; only after an external manual transfer succeeds may the administrator record its method and reference. This is not a provider payout, escrow, or an automatic transfer. The seller sees the confirmed payout destination and instructions in Bengali and English after both confirmations.
- Shop events have a persistent, separate notification center at `/shop/notifications`; authenticated users see their own order, payment, delivery, refund, payout, and product-review updates there, independently of social notifications.
- Messenger group calls use a LiveKit SFU. Configure `LIVEKIT_URL` (the project's WebSocket URL, usually `wss://...`), `LIVEKIT_API_KEY`, and `LIVEKIT_API_SECRET` on the backend from a LiveKit Cloud project or your self-hosted LiveKit server; keep the API secret private and restart/redeploy the backend after setting them. Group members receive a short-lived room token only after server-side membership is verified; encrypted groups additionally require a current per-member call-key envelope before the token is issued.
- Messenger end-to-end encryption is opt-in for direct text/media and admin-enabled group text/media/calls. Encrypted attachments and voice notes are encrypted in the browser with a fresh AES-GCM key; their names, MIME types, captions, and decryption keys are carried inside the encrypted message. The server stores and serves only opaque attachment bytes. In Messenger settings, users can save a recovery backup encrypted in the browser with a passphrase (minimum 12 characters) and restore it on another device; the server stores only the encrypted backup. Losing both the original device key and the recovery passphrase makes encrypted history and media unreadable. Compare direct-chat safety codes through a trusted channel. Direct calls use WebRTC's encrypted peer-to-peer media transport, but are not protected by the Messenger message-key system. Calls in groups without group E2EE use LiveKit without app-level E2EE. Text forwarded into an encrypted direct chat is encrypted for that chat.
- Messenger attachments support common audio formats including WebM, Ogg, MP3, M4A/MP4, AAC, WAV, FLAC, and Opus, alongside images and documents, up to 500MB per file. Uploads are staged on disk rather than buffered in backend memory, and large Cloudinary uploads use chunked streaming. The deployed host's request/disk limits and Cloudinary account limits still apply; browser memory use may also be significant for end-to-end-encrypted files. The document scanner can combine up to 100 processed pages into one PDF attachment.
- Messenger location sharing sends a one-time pin rounded to four decimal places only after the user confirms the selected conversation. It does not continuously track location; browser location access requires HTTPS or localhost.
- Direct and group video calls start with the front camera; local front-camera previews are mirrored, while remote video is not. Camera switching attempts to restore the previous camera if the requested camera is unavailable. Audio output selection is available only in browsers that expose selectable output devices; mobile browsers that do not expose an earpiece/loudspeaker selector leave routing to the operating system.

Never commit `.env` files or production secrets.
